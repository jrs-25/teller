## Decisions made
- Classify, then apply policy. The model never chooses the action.
- The seam is at policy resolution. Categories are YAML entries that pick from fixed handlers (`draft_response`, `route_with_package`, `escalate`).
- Per-category fields: action, member_response_allowed, destination, package_fields (allowlist), confidence_threshold, precedence, rollout_stage, owner.
- v1: one primary category per intake, chosen by precedence. Secondary tags deferred.
- **Teller sits beside the ticketing system, not in front of it.** Tickets are created as today; Teller reads them and writes decisions back (tag, draft as internal note, reroute). If Teller fails, the ticket stays in the manual queue. (RFC §3, §1 diagram)
- **Ingestion: webhook.** Thin payload (ticket ID only), fetch the ticket via API, verify signature, re-read before writing back and back off if an agent already has it. At-least-once is enough, since a missed ticket is handled manually. (RFC §3)
- **Prototype builds:** thin webhook endpoint (`POST /webhooks/ticket-created`, so FastAPI), signature check, fetch from the mock ticketing adapter, pipeline, write-back to the mock ticket, back-off check, and idempotency/loop guard (skip if tagged `teller_processed`).
- **Writing to the live ticketing system (RFC §3):** everyday writes are only internal note, tags, move group (the v1 approval gate). The one member-visible write, `send_public_reply`, exists for the future `send` stage but is locked behind three code checks: global `auto_send_enabled` (off in v1; Compliance + Support lead sign-off), category `rollout_stage: send`, and `member_response_allowed: true` (so never compliance). CI asserts no member-visible write with v1 config, and that no config lets compliance reach it. Good-guest rules: dedicated low-privilege service account, small reversible writes only (never status/priority/SLA/solve), one note per ticket, re-read and conditional update, review existing triggers with the Support admin before go-live, API rate budget. Support owns the kill switch (turn off the webhook trigger).
- **Documented only, for FDE:** durable queue behind the webhook (SQS/Kafka), scheduled sweep for missed webhooks, backlog skip, follow-up messages. (RFC §3 table)
- **Platform-agnostic, Zendesk as the worked example** (Joel: companies switch ticketing systems after mergers or for better products). The adapter is a second seam: vendor-neutral contract (`get_ticket -> Intake`, `add_internal_note`, `add_tags`, `move_to_group`, no public-reply method); webhook signatures, field IDs, group IDs stay inside it. (RFC §0.2, §3)
- **Routing already exists in their system** (Joel's baseline). Teller does the forwarding step an agent does today, through the same mechanism (move to an existing group). No routing UI, no new paths to Product/Compliance. `destination` = name of an existing route. (RFC §0.2, §3)
- **Rollout ladder per category** (RFC §3): `off | shadow | suggest | act | send` (`send` is after v1; enabled by config, not code, behind the three locks). Shadow is blind (CSRs see nothing). Routing and replies climb separately; replies are always sent by a CSR. Order by cheapness of mistakes; volume % within a stage. Support lead promotes on agreed evidence; automatic demotion. Never route away from Compliance. Prototype: pipeline checks stage before any ticket write, plus one test.
- **What Teller writes to the ticket** (RFC §3): only the tag `teller_processed` and one internal note (header with stage, category, confidence tier, decision ID; draft reply; why; sources; check before sending; flag macro). Reporting by category/confidence comes from Teller's decision record, not tags.
- **v1 categories** (RFC §1): `general_qa` (draft), `product_feedback` (route to existing Product queue + summary + thank-you draft, sent by whoever works that queue), `compliance` (route, never reply), `suspected_fraud` (config-only example). Account issues fold into general_qa: drafted if the KB answers it, escalated if it depends on the member's own account data. Escalate and fallback are outcomes, not categories. Thresholds/precedence: compliance 0.0/100, product_feedback 0.6/50, general_qa 0.8/10 (placeholders, tune on past tickets). `suspected_fraud` (0.0/90) is NOT in the initial config: add it after the build as its own config-only commit, as proof of the seam. Teller doesn't write a category field to the ticket in v1 (the CSR's own label/action is the answer key for shadow mode).
- **"Only write to the version Teller read"** (RFC §3): one atomic ticket update (note + group + `teller_processed` tag together), sent as a conditional update; if the ticket changed since read, re-read and reprocess (max 2), then leave to a human. Note carries a version stamp ("based on messages as of…"). Teller does NOT watch follow-ups in v1 (Joel: slippery slope); rerunning the tripwire on follow-ups is "next". At `send`, re-check version before sending. Prototype: build the atomic + conditional update and a test for the race.
- **Edge-risk review, decided:** #3 one atomic update (prototype). #4 attachments + #6 tickets Teller shouldn't touch = one **eligibility check** at validate (unverified member, agent-created, non-English, has attachments → no write, stays manual, reason recorded); also set in the webhook trigger (RFC §1). Prototype builds it. #7 kill switch doesn't recall posted drafts: noted as known limitation in RFC §3, not built. #1 handled by the version rule.
- #5 prompt injection: brief note in RFC §2 only (output check at the safety gate: link allowlist on drafts; input denylists are weak). **Not built** in the prototype.
- **Parked bucket: logging & reporting** (Joel will return to it). Contains #2 rubber-stamping, #8 holdout / metric bias after shadow, and the open question of what lives in Teller's decision record vs. what comes from Zendesk reporting (e.g. compare `teller_processed` tickets vs. not). Claude's notes from discussion: Teller must own the decision record (explainability, incident recovery); outcomes (speed, reopens, CSAT, who sent) come from Zendesk; compare within category or via a holdout; consider tagging only at `suggest`+ so shadow tickets don't blur the comparison.
- **One config file per category** (`config/categories/<id>.yaml`) with a CODEOWNERS line per file, so ownership is really separated (CODEOWNERS is per file). Adding fraud = one new file + one CODEOWNERS line. (RFC §1) Prototype: build this layout + example CODEOWNERS.
- **Open (category separation):** #2 regression check, reframed per Joel: adding fraud *should* take tickets from general_qa; the check makes shifts intended and visible (labeled fixtures; only fraud-labeled tickets move; nothing leaves compliance; print a "moved X → Y" report for owners to approve). **Decided: describe only** (RFC §1, end of "Adding a category"). #3 **safety floor in code: BUILD** (RFC §1 "The safety floor"): validator at load + CI refuses configs where compliance/tripwire-forced categories allow member reply or `send`, where compliance isn't highest precedence with threshold 0.0, or where `package_fields` names an unknown/unsafe field. Test tries each forbidden setting.
- **Compliance detection = most important open decision** (RFC §0.3, owner Compliance & Legal). Working default (RFC §2): keyword tripwire + separate single-purpose compliance check; either only pushes toward compliance; three outcomes: clear → Compliance, gray → Support human, no draft, "possible compliance" flag, clear-of → normal; check failure → no draft. Fixed Claude's earlier bug: compliance threshold 0.0 would have sent nearly every ticket to Compliance; now 0.3 placeholder and the safety floor says "lowest threshold of any category". Prototype: mock compliance check; disguised-complaint fixture caught by the check, misbehaving-classifier case caught by keywords; gray-zone fixture.
- **No text in logs, not even redacted** (Joel agreed): redaction misses can't leak to the most widely copied store; testable exactly; debugging goes via decision record. Same rule for **traces** (IDs/timings only; LLM observability prompt capture off). **Every miss becomes a synthetic fixture** (not the real ticket). (RFC §2)
- **§2 proposals accepted, in pipeline order:** redaction first (only the redactor sees raw text; member data never reaches the model provider); tripwire + compliance check; gate checks twice + rejects drafts containing redaction tokens; CI safety test incl. fixture "compliance complaint containing an account number still goes to compliance".
- **Knowledge base** (RFC §3 "Using the knowledge base without ingesting it"): only draft_response uses it; wrap the help center's existing search via a KB adapter `search(query)`, no ingestion in v1 (Joel: ingesting a KB is no small feat); no article → no draft → escalate; drafts cite sources (gate checks); public help center only; KB down → no draft; build ingestion only when "no KB answer" escalation rate blocks the 80% goal. **Prototype: mock KB (few fake articles, keyword lookup) + no-match→escalate test only.** Rest described. Stale-KB additions (RFC §3): show article age + warn if old; never quote rates/APYs/fees (link or escalate); KB owners review most-relied-on articles before general_qa leaves shadow; "possibly outdated" list → logging bucket.
- **Member profile service: NOT used in v1** (Joel). Listed under "left alone" (RFC §3); new subsection "The member profile service, after v1" with the two future uses (safety flags → no draft; products held → right article), accepted v1 risk (open-dispute member could get a routine draft; covered by compliance checks + CSR review), and a precondition for `send`. Degraded-mode prototype should use the KB (or ticketing API) as the failing dependency instead. **Added after Joel asked what was essential about it:** the profile service is how account issues (one of the brief's four intake types) get resolved, so leaving it out caps v1's reach toward 80%. RFC now states that cost (shadow measures account-issue share → likely first post-v1 investment), and designs (not builds) its data rules (§2: allowlist of flags/product types, never balances/account numbers) and failure behavior (§4).
- **Degraded mode** (RFC §4): failure → write nothing, record reason; notes only when Teller has something useful (low confidence guess, gray flag, no KB answer). Prototype: mock deps that can fail; tests: KB down → no draft; compliance check down → no draft, but keyword-matched compliance still routes.
- **Prototype must include:** a CI test that every ticketing adapter exposes only the allowed write methods, so a new adapter can't add a public reply (the RFC §3 promises this). Zendesk-shaped JSON fixtures (webhook, ticket API response) for routine, feedback, compliance, and a disguised compliance case, with fake canary account numbers.

## AI Leverage Log candidates (overrides and pushback)
- Claude suggested writing RFC §1, 2, 4 first and deferring §3 because it "doesn't drive code." Joel pushed back. Looking again, rollout stage, kill switch, and system adapters *do* belong in the build contract, so §3's decisions moved up front.
- Joel steered the design to start from the external system: "how does input arrive from their case management system?" That produced the "beside, not in front" decision, which also simplified §2 (no separate store of real values) and gave §4 a fail-safe default.
- Joel raised ingestion (event-driven vs. scheduled polling) from a similar project in Joel's day job. Claude proposed webhook + queue + sweep + idempotency; Joel chose to build only the webhook in the prototype and document the rest as FDE work.
- Joel flagged the live ticketing system as a likely interview gotcha ("it's the system actively in use, so be considerate in how Teller posts to it"). That surfaced the biggest single risk in the design: a public comment emails the member. The fix is structural, since the adapter can't post one, and it turned an integration detail into the v1 approval gate.
- Joel decided to design platform-agnostic with Zendesk only as the example, after Joel's own research suggested Bankrate's public help center runs on Zendesk. Claude also corrected that research's suggested adapter ("create case, set status"), which conflicted with the beside-not-in-front and never-change-status decisions.
- Claude proposed seven reporting tags plus custom fields; Joel cut it to one tag (`teller_processed`) as overly complicated. Reporting detail moved to Teller's decision record.
- Joel asked for a per-category flag to enable public replies once confidence is earned. Claude pushed back (it turns a structural guarantee into a config setting; v1 forbids it) and proposed requiring a code change. Joel kept the goal of "possible without code changes" and accepted a middle path: a `send` rung behind three locks, never for compliance, with the tradeoff stated in the RFC.
- Claude proposed watching follow-up messages to catch a compliance concern raised after the draft. Joel rejected it as a slippery slope of edge cases and pointed out the same race exists between fetch and post. Result: one rule ("only write to the version Teller read") via conditional update, plus a version stamp in the note, instead of follow-up handling.
- Joel questioned whether a keyword tripwire was enough; Claude proposed a second, model-based compliance check. Joel then pushed on Claude's own example ("fees nobody told me about" could be routine), and chose to elevate "where is the compliance line" to the RFC's top open decision, owned by Compliance & Legal. Along the way Claude caught its own earlier error (threshold 0.0 would route nearly everything to Compliance).
- Joel noticed the KB wasn't really incorporated, and flagged that ingesting a KB is a big effort. Result: wrap the existing help-center search, no ingestion in v1, "no article, no draft" so weak search costs usefulness not safety, and build ingestion only when the "no KB answer" rate justifies it. Joel limited the prototype to a mock KB + one rule.
- Joel drew on prior experience with an analogous KB (for VA claims processors): RAG needs a full chunking/ingestion strategy, and KBs are often out of date. That reinforced no-ingestion in v1 and added stale-content safeguards Claude hadn't proposed (age warnings, no quoting rates/fees, KB health check before general_qa leaves shadow). Joel kept the personal experience out of the RFC; use it in the live session.
- Joel sensed something essential was missing about the member profile service (named twice in the brief). Claude had let it drop to "not in v1" without stating the cost; the gap was that it's the path to resolving account issues and so to the 80% goal. Kept out of v1, but the RFC now states the cost and designs its data and failure rules.
- Joel had Claude turn the brief into a working constitution (`CLAUDE.md`, committed for reviewers): priority order, a "build test" defaulting to stub/describe/hand off, and a standing instruction to call out scope creep and push back. First application: Claude flagged that the webhook endpoint itself is plumbing; the value is in fetch-on-read, re-read before write-back, and the loop/idempotency guard.
- Joel chose to write the RFC first as the build spec. Claude agreed but flagged the risk of over-polishing it and added a "prototype contract" section to connect the RFC to the code.
